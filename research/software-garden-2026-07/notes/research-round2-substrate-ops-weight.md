## 1. Kafka-API-compatible engines (web-verified 2026-07-29)

### Redpanda — the lightest true-Kafka-API self-host
- **Ops shape:** one C++ binary containing broker, Schema Registry, HTTP proxy, and Raft consensus — no ZooKeeper, no KRaft, no JVM ([redpanda.com capabilities](https://www.redpanda.com/data-streaming/platform-capabilities), [gocodeo deploy guide](https://www.gocodeo.com/post/deploying-redpanda-high-performance-streaming-without-zookeeper)). On k8s: Helm chart (simple) or Operator (lifecycle management) ([docs: k8s deployment overview](https://docs.redpanda.com/current/deploy/redpanda/kubernetes/k-deployment-overview/), [HA guide](https://docs.redpanda.com/current/deploy/deployment-option/self-hosted/kubernetes/k-high-availability/)). Built-in Schema Registry removes a whole deployable vs. Kafka+Confluent-SR — directly relevant to T1.1.
- **Licensing:** Community Edition = BSL 1.1, free, source-available, each merge converts to Apache 2.0 after 4 years ([Redpanda BSL announcement](https://www.redpanda.com/blog/bsl-source-available-license), [license file](https://github.com/redpanda-data/redpanda/blob/dev/licenses/bsl.md)). **Tiered Storage, Continuous Data Balancing, Remote Read Replicas are Enterprise (RCL) features** ([licensing docs](https://docs.redpanda.com/current/get-started/licensing/overview/), [tiered storage docs](https://docs.redpanda.com/current/manage/tiered-storage/), [edition comparison](https://www.redpanda.com/data-streaming/compare-platform-editions)).
- **Greenwood property check (Community):** keyed ordering ✓, compaction ✓, replay-from-offset ✓, idempotent producer + transactions ✓ (Kafka wire protocol), tiered storage ✗ (paid). **But** — see §6: at M1/small-fleet scale, tiered storage is a cost optimization; payloads-by-reference (MinIO) + snapshot-bounded hot retention (both already engine-independent D6 adoptions) keep the on-disk log small. The KIP-405-excludes-compaction caveat is moot when nothing tiers.
- **Small-cluster viability:** single-node dev mode is first-class; production guidance is 3 brokers; a 3-pod StatefulSet with PVCs on bc-prod is exactly "one new stateful app deployed via kploy."

### AutoMQ — D6's pick, re-weighed for *this* operator
- **What it is:** a Kafka **fork** — Kafka's compute layer (so compaction runs via the real LogCleaner, transactions/idempotence inherit Kafka semantics) over S3-compatible object storage with a small WAL for the durable write path; stateless brokers; Apache 2.0 ([automq.com](https://www.automq.com/), [GitHub](https://github.com/automq/automq), [FAQ](https://www.automq.com/faq)). Works against MinIO (self-hosted S3) per its own positioning ([blog: Redpanda tradeoffs comparison](https://www.automq.com/blog/redpanda-for-kubernetes-operational-tradeoffs-and-kafka-compatible-alternatives)).
- **The catch for bc-prod:** it is still a JVM Kafka-lineage system — brokers + WAL volumes + controller/metadata + S3 dependency chain. Every economic argument in D6 (no 3× replicated NVMe, no cross-AZ tax) is real **at fleet scale on cloud object storage**; on a single shared k8s cluster whose "S3" is MinIO in the same cluster, the wins shrink to ~nothing at M1 volume while the operator surface (JVM tuning, WAL sizing, S3-path failure modes — a new class of incident for a junior) stays. Chattermax Phase 8's verdict was rendered against exactly this shape of stack.
- **Maturity 2025–2026:** active, commercially backed, AWS Marketplace listing ([AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-mtkwt73meb222)); its content-marketing volume (most "Kafka alternatives 2026" comparisons are AutoMQ's own blog) means third-party ops testimony is thinner than Redpanda's — treat "easy to run" claims as vendor-sourced.
- **Verdict:** right *endgame* engine (keeps D6's economics and kills the KIP-405/compaction conflict), wrong *first* deployment for a junior-operated cluster. Adopt when measured volume or multi-AZ cost justifies it — with the log behind a trait (finding 14), that swap is an ops migration, not a rewrite.

### WarpStream — excluded for self-host posture
- BYOC only: stateless agents in your VPC against your S3, **metadata/control plane hosted by Confluent** ([warpstream.com/pricing](https://www.warpstream.com/pricing), [Confluent acquisition](https://www.confluent.io/blog/confluent-acquires-warpstream/)). No air-gapped/fully-self-hosted mode → fails the default posture outright, independent of the KB-documented compaction ceilings (3M keys/128 GiB/job, immutable `cleanup.policy`) and the Confluent→IBM ownership chain (closed 2026-03-17, per D6). Keep as the "someone else runs it, data stays in our account" fallback if posture changes.

### Bufstream — watchlist
- Kafka-compatible broker over object storage + off-the-shelf metadata (**Postgres**, etcd, or Spanner) ([buf.build/product/bufstream](https://buf.build/product/bufstream), [docs](https://docs.bufbuild.ru/bufstream/)). The Postgres-metadata + MinIO-object-store combination maps neatly onto what bc-prod already runs — architecturally the most bc-prod-shaped of the S3-native engines.
- Commercial licensing (pricing pitched as "8× cheaper than Kafka *inclusive of licensing fees*", AWS Marketplace listing ([announcement](https://webflow.buf.build/blog/bufstream-is-now-on-the-aws-marketplace))); ~500 ms p99 latency class (same as WarpStream). Licensing terms for a tiny self-host deployment **[verify at buf.build/pricing]**. Not a candidate for Aug-16; revisit at M2 if the Postgres-metadata shape appeals.

## 2. Non-Kafka alternatives (web-verified except where tagged)

### NATS JetStream
- **License risk closed:** Synadia's April-2025 attempt to pull NATS from CNCF and relicense to BUSL ended May 1 2025 — CNCF keeps trademark/repos, NATS server stays Apache 2.0 ([CNCF statement](https://www.cncf.io/blog/2025/05/01/protecting-nats-and-the-integrity-of-open-source-cncfs-commitment-to-the-community/), [The New Stack](https://thenewstack.io/cncf-and-synadia-reach-an-agreement-on-nats/), [The Register](https://www.theregister.com/2025/05/02/cncf_synadia_nats/)).
- **Ops:** the lightest option that isn't Postgres — single Go binary, tiny footprint, mature Helm chart. Genuinely at/below Redpanda's ops weight.
- **Greenwood property check:** replay-from-sequence ✓; per-subject ordering ✓; idempotence only via `Nats-Msg-Id` dedup **window** (default 2 min; per-subject discard-new gives a bounded-infinite variant) — weaker than epoch-fenced producers ([JetStream model deep dive](https://docs.nats.io/using-nats/developer/develop_jetstream/model_deep_dive), [dedup blog](https://nats.io/blog/new-per-subject-discard-policy/)); **compaction ✗** (KV store = max-msgs-per-subject retention, not log compaction with history); **tiered/S3 storage ✗** (nats-io #3871/#5486, per D6). Two of five required properties missing → **D6's rejection re-affirmed**, now with the license cloud also cleared away as a reason to revisit.

### Apache Pulsar (brief)
Three operated tiers (brokers + BookKeeper + ZK/Oxia) + RocksDB inside bookies; realistic production floor ~9 nodes; BookKeeper debugging expertise scarce ([Pulsar ZK/BK admin docs](https://pulsar.apache.org/docs/next/administration-zk-bk/), [Conduktor comparison](https://www.conduktor.io/glossary/kafka-vs-pulsar), [Confluent comparison](https://www.confluent.io/kafka-vs-pulsar/)); compaction fails on S3-tiered topics (apache/pulsar#8282, unfixed — per D6). The single heaviest option surveyed; **rejection re-affirmed**.

### The "just Postgres" school
- **Pattern** (well-trodden): append-only events table (`bigserial` global position = the offset; `(stream_id, stream_version)` unique = keyed ordering + optimistic concurrency), transactional `NOTIFY` for wake-up, `FOR UPDATE SKIP LOCKED` for competing workers, outbox where cross-system delivery matters ([Postgres-as-message-bus writeup](https://thinhdanggroup.github.io/postgres-as-a-message-bus/), [eugene-khyst/postgresql-event-sourcing](https://github.com/eugene-khyst/postgresql-event-sourcing), [pgmq LISTEN/NOTIFY variant](https://github.com/oliverlambson/pgmq)). message-db (Eventide) and Marten are the production-grade proofs of event-store-on-Postgres.
- **Greenwood property check:** append-only ordered log ✓ (global sequence + per-stream order — *stronger* than Kafka's partition-only order); keyed ordering ✓; replay-from-offset ✓ (a SQL cursor); idempotence ✓ (unique `event_id` constraint — simpler and stronger than producer sessions); **compaction ✓ by dissolution** — a projection is a table updated by a fold, so "compacted topic" stops being a concept, and D6's open problem (monotone `claim_id` keyspace defeating latest-per-key compaction; TTL-after-terminal-state vs DB-backed projection) *is answered for free* — the DB-backed projection is the native form; tiered storage ✓-ish (partition by month, archive old partitions to MinIO as parquet/dump — hand-rolled but boring and cron-shaped).
- **What's genuinely lost:** consumer-group rebalancing protocol (hand-roll: SKIP LOCKED workers + a positions table — M1 needs exactly one consumer per projection), big fan-out throughput (irrelevant: topic 11 puts 500 agents at ≤10 MB/s and M1 at ~one agent), Kafka ecosystem tooling (Connect/Flink — nothing in M1–M3 uses them), and the literal Kafka API (matters for D6's wording, not for P0 — see §6).
- **Ops:** **zero new deployables.** Postgres on bc-prod is provisioned via `bc-prod.yaml`, backed up on schedule, monitored, and already inside kploy's story. This is the only option *at* the kploy bar rather than a notch above. Ceiling before pain (single-table append throughput, autovacuum on hot projections) sits orders of magnitude above M1 traffic.

## 3. Managed escape hatches — training knowledge, tagged for verification
*(Everything in this section: cross-check when web tooling returns; pricing moves quarterly.)*

- **Upstash Kafka is gone** — deprecated and shut down in 2025 (announced late 2024; service termination ~March 2025), with Upstash pivoting to Redis/QStash/Workflow **[verify: upstash.com blog]**. It was the only true scale-to-zero, per-message-priced hosted Kafka. Its death is itself a signal: tiny-workload hosted Kafka is a hard business, and the "cheap managed Kafka" shelf is nearly bare.
- **Confluent Cloud Basic**: $0/month base, usage-priced (per-GB ingress/egress/storage + partition-hours); a Greenwood-M1-sized workload would land in single-digit-to-tens of $/month; free credits for new signups **[verify: confluent.io/pricing]**. Functionally complete for Greenwood (compaction, transactions, "infinite" tiered retention on paid tiers). Two strategic negatives: agent event content derives from *client* work (a consultancy confidentiality question the KB hasn't answered — payloads-by-reference to bc-prod MinIO with only hashes leaving would blunt it), and Confluent is now IBM-owned (D6's vendor-risk line).
- **Redpanda Serverless**: pay-as-you-go, near-$0 entry for tiny throughput, but partition/feature caps at the low tier **[verify: redpanda.com/pricing]**. Same off-prem data consideration.
- **MSK Serverless**: ~$0.75/cluster-hour ≈ **$540+/mo floor before a byte flows** **[verify]** — not consultancy-cheap; provisioned MSK on t3.small is cheaper but returns broker ops to you; and bc-prod isn't AWS-native anyway.
- **Verdict:** a managed Kafka tier is a credible *dev/CI environment* and an emergency bridge (drop-in with the Kafka API preserved), not the prod posture. MEDIUM relevance to both decisions — it exists as an option, which lowers the risk of choosing the Kafka API generally, but it should not be M1's substrate.

## 4. Durable execution for the M1 runtime slice — training knowledge, architecture stable
The tempting reading of M1 ("event-sourced loop, crash-resume, cache-hit on resume") is "that's just durable execution — buy Temporal/Restate/DBOS/Inngest." The P0 test says no:

- **Temporal**: self-host = frontend/history/matching/worker services + Postgres/MySQL/Cassandra (+ Elasticsearch for visibility) — several notches past kploy for a no-platform-team shop; Temporal Cloud is consumption-priced. Deeper problem: its event history is **per-workflow**, capped (51,200 events / 50 MB — already cited in topic 11 as the anti-pattern Greenwood's snapshots avoid), owned by Temporal's store, truncated on completion/continue-as-new. There is no shared keyed spine, no replay-as-public-API across agents, no projection/compaction surface, no lineage across workflows. **State = fold of *the* log** becomes **state = Temporal's private checkpoint of *this* workflow** → P0 betrayed at the foundation, and D4 (hermetic replay evals off the log) and Rootlines (cross-agent lineage) lose their substrate.
- **Restate**: the only one at the right ops weight — single Rust binary, embedded replicated log (Bifrost), k8s-friendly; SDK journaling gives crash-resume almost exactly shaped like T3.x. Server license is source-available/BSL-class, SDKs permissive **[verify: restate.dev]**. Same P0 objection in milder form: the journal is per-invocation and truncated after completion; it is Restate's internal record, not Greenwood's queryable, foldable, ACL'd spine. Worth *stealing from* (journal + suspend/resume + deterministic replay of recorded results mirrors topic 06's design), not building on.
- **DBOS**: a library (TS/Python) checkpointing workflow steps into **Postgres** — zero added infra, the lightest of all. But it's step *checkpointing*, not event sourcing: the recorded state is operational recovery data, not the system of record you fold projections from. If Greenwood were not itself an event-sourcing thesis, DBOS-on-Postgres is what M1 would be; since it is, the owned pattern (events table + fold + snapshot) *is* the deliverable.
- **Inngest**: event-driven durable step functions; managed-first, self-host exists (server + Postgres/Redis) **[verify current self-host maturity]**. Event log retention/replay is product-tier bound; same category error as Temporal for P0.
- **Verdict:** starting M1 on any of these would ship crash-resume while **betraying P0** — the log they keep is theirs, per-workflow, truncated, and unprojectable; Greenwood's entire M2+ (claims, trust folds, lineage, hermetic evals) consumes the log as a first-class queryable artifact. The "owned queue+worker+checkpoint" pattern on the chosen log substrate is not incidental M1 work — it *is* M1. (HIGH clarity for the stack decision; MEDIUM for the date — it removes a tempting shortcut.)

## 5. Runtime language — training knowledge + in-house evidence
- **Rust / rust-rdkafka** (bindings over librdkafka): mature and maintained; librdkafka has shipped idempotent producer + transactions (EOS) since 1.4/1.5 — T1.3's `acks=all` + idempotence + keyed publish + replay-from-offset are all covered. **In-house proof: Chattermax Phase 8 already shipped an rdkafka idempotent producer with `acks=all`** (`notes/repo-chattermax.md`) — the team has walked this exact path. Costs: a C dependency in the build, occasional async-integration awkwardness, and no streams framework — you hand-roll consume→fold→emit.
- **JVM / Kafka Streams**: the only real streams *framework* with end-to-end EOS (state stores + changelog topics + transactions). But Greenwood's folds are bespoke by design — a lineage DAG, byte-deterministic prompt assembly, epoch-fenced folds; none of that wants the KStreams DSL, and adopting it buys a JVM, a framework's opinions, and a second language into a Rust shop whose founders are systems/runtime people. Kafka Streams also binds you to *broker-side* Kafka semantics precisely where §6 wants substrate freedom.
- **Go / franz-go**: the strongest non-JVM client by KIP coverage incl. EOS/transactions; a fine choice in the abstract, but nothing about Greenwood pulls toward Go against the team's Rust center of gravity (Grumpy notwithstanding).
- **Note that de-risks the whole question:** Greenwood's stream logic is hand-rolled *in every language option* (Kafka Streams was already ruled out on design fit). So client-library maturity only gates the thin log adapter (T1.3) — and if M1's log is Postgres (§6), the M1 client is sqlx/tokio-postgres, fully mature, and the rdkafka dependency arrives only with the engine swap.
- **Recommendation: Rust.** Team pedigree, Chattermax code/experience reuse (envelope handling, idempotent-producer wiring, Prometheus patterns), single language across bus-side services and runtime, and byte-level control over prompt assembly (the determinism spine of topics 06/07) where GC-language string handling invites accidental nondeterminism. Score: HIGH/(a), HIGH/(b) — this unblocks P1/P2 immediately.

## 6. Recommendation — ranked substrate for M1

**The bar, restated:** kploy = 0 notches (it's the baseline). One new stateful service with one binary and a Helm chart = 1 notch. A JVM fork + WAL + controller + S3 dependency chain = 2+. Temporal's service constellation = 3. Pulsar = off the chart. Chattermax Phase 8 already established where this team draws the line, and R1 makes the first user a junior.

1. **Postgres-backed event log behind Greenwood's own thin log trait** (append / keyed-ordered read / replay-from-position / consumer positions; projections as tables; `NOTIFY` for tailing; MinIO for payloads-by-reference). **Zero notches** — every component is already on bc-prod, backed up, and inside kploy's deploy story. Fastest credible path to Aug-16; P0 is fully honored (P0 mandates event sourcing, *not* Kafka — the fold, the immutable spine, ACL'd `confirmed`-vs-`raw`, epoch fencing, snapshots all express naturally in SQL); and D6's one genuinely unresolved technical problem (monotone claim keyspace vs compaction) dissolves rather than needing TTL machinery. **Honest cost:** this re-opens the *decided* "Kafka API as substrate" line — T1.2/T1.3/T3.3 are written Kafka-native and would be re-cut against the trait (a day of spec work, and M1 needs none of the consumer-group machinery anyway); and the known failure mode is the "temporary" shim becoming load-bearing forever — mitigate by making the trait's semantics deliberately Kafka-shaped (offsets, keys, positions) and CI-testing the trait against a real Kafka-API engine from day one.
2. **Redpanda Community, 3-node StatefulSet on bc-prod** — the choice if Terra holds the decided Kafka-API line for M1 (a defensible call: no adapter drift, ecosystem intact, D6 engines stay drop-in). **One notch** — a single new binary/chart, no ZK, no JVM, Schema Registry included; compaction/transactions/idempotence in the free tier. Accept: no tiered storage (enterprise) → hot log lives on PVCs, bounded by snapshots + payloads-by-reference (already the design); BSL-not-Apache source availability.
3. **AutoMQ on MinIO — the D6 endgame, deferred to M2+.** Keep it as the named target engine (its economics and compaction-on-S3 story remain the right fleet-scale answer); adopt when measured volume, retention pressure, or multi-AZ reality justify a second notch, and run D6's open produce-latency measurement then. Do not make a junior's first month include debugging a JVM/S3 WAL path.
4. **Managed Kafka (Redpanda Serverless / Confluent Basic)** — dev/CI environments and emergency bridge only; near-$0 entry **[verify pricing]**, but off-prem client-derived data + IBM-owned Confluent argue against prod use; Upstash's exit shows the tier's fragility.
5. **WarpStream / Bufstream** — WarpStream excluded (hosted control plane violates self-host posture; compaction ceilings; vendor chain). Bufstream to the watchlist: its Postgres-metadata + object-store shape is the most bc-prod-like of the S3-native engines if licensing suits.
6. **NATS JetStream / Pulsar / Kinesis / PubSub** — rejections re-affirmed (NATS now with the license question also closed; it still lacks compaction semantics and an S3 tier).

**Durable execution:** not as substrate — Temporal/Restate/DBOS/Inngest keep private, truncated, per-workflow logs and would betray P0 (state = fold of *the* log) plus starve D4/Rootlines of their input. Steal Restate's journal-and-suspend shape; build the owned pattern on the chosen log — that pattern *is* M1's P3.

**Language:** Rust (rdkafka when a Kafka-API engine lands; sqlx if #1 is chosen). Unblocks P1/P2 now.

**What would change the ranking:**
- Terra re-affirms "Kafka API from day one" as non-negotiable → #2 becomes #1 (and the answer to "is that within the ops bar?" is yes — one notch).
- bc-prod DBA/capacity policy against large append-only tables or LISTEN/NOTIFY connection pressure → #2.
- M1 scope grows to real multi-agent fan-out or anything needing Connect/ecosystem → #2, with #3 pulled earlier.
- A platform/SRE hire lands before 2027 planning → pull #3 (AutoMQ) forward to M2.
- Measured AutoMQ produce latency on MinIO disappoints, or MinIO ops prove flaky under WAL-ish load → AutoMQ demoted behind Redpanda-with-enterprise-license as the scale path.
- Confidentiality analysis clears payload-by-reference events for off-prem metadata → managed tier becomes a viable M1 shortcut (it wasn't ranked on ops weight — it's the cheapest of all — but on posture).

**Open items produced by this round:** verify the eight **[verify]** tags (managed pricing, Upstash shutdown date, Restate license, Bufstream self-host licensing, franz-go currency); decide #1-vs-#2 with Terra explicitly as "re-open decided Kafka-API line: yes/no"; if #1, re-cut T1.2/T1.3/T3.3 against the log trait and add the CI conformance job against a Kafka-API engine; write the confidentiality position on off-prem event metadata into the KB.
