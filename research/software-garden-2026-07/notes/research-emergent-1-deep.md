# Knowledge freshness — deep pass

**Scope:** extends `research-emergent-1.md`. That note covered docs-as-code drift CI (Fiberplane drift, Dosu, Swimm, oasdiff), two-date frontmatter (updated/verified, OKF, Atlan), temporal RAG papers, Zep/Graphiti bi-temporal memory, and "don't ask the LLM to track freshness." **Nothing below repeats that.** This pass goes into (1) what an event-sourced substrate gives you for free, (2) freshness *contracts* as practiced in the data-engineering world, (3) mechanical index-sync for derived stores, and (4) tool-level metadata schemas and 2025-26 practice the first pass missed.

**Release lens:** Aug 16, 2026; junior operator; 4-5 apps on bc-prod/kploy; greenfield Kafka event-sourced bus (Greenwood).

## 1. The event-sourcing dividend: freshness is derivable, not declared

The first pass treated freshness as metadata to be maintained (two dates, TTLs, drift anchors). An event-sourced substrate changes the economics: **for any knowledge view built as a projection of the log, staleness is an exact, machine-derived quantity** — no human ever stamps anything.

### 1.1 Checkpoint lag as the staleness primitive

- EventSourcingDB's best-practices guide ([Read-Model Consistency and Lag](https://docs.eventsourcingdb.io/best-practices/read-model-consistency-and-lag/)) states the mechanism plainly: track "the latest event ID or timestamp that the read model has applied" and compare it with the head of the stream; express lag either as **seconds of delay or number of unprocessed events**, per domain requirements. Handlers resume from a checkpoint (`lowerBound`), which bounds recovery after failure.
- The same lag concept appears across the CQRS literature as a first-class design parameter — "you must decide acceptable staleness per use case" ([TheCodeForge on CQRS projection lag](https://thecodeforge.io/system-design/cqrs-pattern/), [event-driven.io on projections and read models](https://event-driven.io/en/projections_and_read_models_in_event_driven_architecture/), [arc42 quality model on event sourcing](https://quality.arc42.org/approaches/event-sourcing)).

**Greenwood consequence (inference):** if the navigator's knowledge views are projections of bus topics, every answer can carry an *exact* provenance stamp derived at render time: `as of event <offset> (<event-time>), N events / M seconds behind head`. This is strictly stronger than the two-date frontmatter model — the two-date model remains necessary only for knowledge that does *not* flow through the bus (human decisions, rationale, external facts). The spec should therefore partition the KB into **projected knowledge (freshness derived)** and **authored knowledge (freshness declared)** and treat the two-date/TTL machinery from the first pass as applying only to the second partition.

### 1.2 Staleness monitoring is a solved ops problem

- Because a projection is just a consumer group, its staleness is standard **consumer-lag monitoring**: LinkedIn's [Burrow](https://github.com/LINKIWI/Burrow) computes consumer health from committed offsets *without manually defined thresholds*; [kafka-lag-exporter](https://github.com/QubitProducts/kafka_lag_exporter) and similar Prometheus exporters **estimate time-lag (seconds) from offset lag**; stock Grafana dashboards exist ([Kafka Lag dashboard](https://grafana.com/grafana/dashboards/11963-kafka-lag/); overviews: [Conduktor](https://www.conduktor.io/glossary/consumer-lag-monitoring), [Redpanda on Burrow](https://www.redpanda.com/guides/kafka-performance-kafka-burrow-partition-lag), [AppsFlyer at Confluent](https://www.confluent.io/blog/kafka-lag-monitoring-and-metrics-at-appsflyer/)).
- **Consequence:** "is the garden's knowledge current?" becomes an alert the junior operator already knows how to read — a Grafana panel — rather than a bespoke KB audit. The mahdi failure ("answering from state frozen ~7 weeks") would have been a screaming red lag metric on day one.

### 1.3 Critical reads go to the source of truth

- EventSourcingDB's guide: for critical operations, **bypass the read model entirely** and "perform a write-side check using the event stream itself." Read-your-own-writes (pin reads to the write path for X seconds after a write) handles the agent-writes-then-reads case ([James Hickey on eventual consistency in event sourcing](https://www.jamesmichaelhickey.com/event-sourcing-eventual-consistency-isnt-necessary/)); "progressive confirmation" — telling the user the change is *being processed* rather than pretending it landed — handles the UX.
- This is the event-sourced generalization of the first pass's "derive, don't quote" rule, and it gives the spec a clean triage: **critical operational claims → live query (log head or live system); routine claims → projection + lag stamp; historical/rationale claims → authored KB + two-date stamp.**

### 1.4 Adjacent proof points

- **Incremental view maintenance** engines show "projections as always-fresh views" is a mature product category: Materialize maintains continuously updated views with strict-serializable consistency and sub-second freshness ([Materialize on AI + fresh views](https://materialize.com/blog/whitepaper-ai/), [RisingWave IVM guide](https://risingwave.com/blog/what-is-incremental-view-maintenance/), [IVM survey](https://materializedview.io/p/everything-to-know-incremental-view-maintenance)). Not release infrastructure — but validates the architecture direction.
- **XTDB v2** is the production database expression of the bitemporal model the first pass found in Graphiti: every row carries **system time** (audit: when the system learned it) and **valid time** (when it was true in the world), queryable via `FOR SYSTEM_TIME AS OF` / `FOR VALID_TIME AS OF` ([What is XTDB](https://docs.xtdb.com/intro/what-is-xtdb.html), [Time in XTDB](https://docs.xtdb.com/about/time-in-xtdb.html), [v2 launch](https://xtdb.com/blog/launching-xtdb-v2)). Greenwood already gets system time free from the log; adding a valid-time field to knowledge events is the cheap 80% of bitemporality.

## 2. Freshness contracts: what the data-engineering world standardized

The first pass covered freshness *scoring* (Dosu, Atlan). The data world went a different, arguably more disciplined route: **declared, per-source freshness contracts checked mechanically.** This is the missed analogue domain, and its schemas are directly liftable.

### 2.1 dbt source freshness — the canonical two-tier contract

- Every source table may declare a `freshness:` block with `warn_after` and `error_after` durations plus a `loaded_at_field` (the timestamp column to check). `dbt source freshness` evaluates `max(loaded_at_field)` against now and emits pass/warn/error; one or both thresholds may be set; **if neither is set, freshness simply isn't computed** — contracts are opt-in per source ([dbt reference: freshness](https://docs.getdbt.com/reference/resource-properties/freshness), [dbt sources](https://docs.getdbt.com/docs/build/sources), [Datafold guide](https://www.datafold.com/blog/dbt-source-freshness/)).
- **Why it matters for the garden:** this is the field-tested *shape* for the tiered-TTL idea in the first pass — two thresholds (soft-warn, hard-error), a declared machine-checkable evidence field, one command runnable in CI or cron. Knowledge-entry frontmatter can copy it verbatim: `freshness: {warn_after: 14d, error_after: 45d, verified_field: verified}` with navigator behavior mapped to tiers (stamp → banner → refuse-and-emit-verification-command).

### 2.2 DataHub freshness assertions — staleness as missed expected change

- DataHub lets you assert **when a table is *expected to change*** and alerts when it doesn't, with pluggable change-detection sources: warehouse **audit log**, information schema, a **last-modified column**, or a **high-watermark column** ([Freshness Assertions](https://docs.datahub.com/docs/managed-datahub/observe/freshness-assertions), [Assertions overview](https://docs.datahub.com/docs/managed-datahub/observe/assertions)). Freshness assertions compose into **data contracts** alongside schema and quality assertions ([Data Contracts in DataHub](https://datahub.com/blog/data-contracts-in-datahub-combining-verifiability-with-holistic-data-management/)).
- **The conceptual addition over the first pass:** age-based staleness ("this is old") and cadence-based staleness ("this should have updated by now and didn't") are *different signals*. The second detects dead pipelines — e.g., a garden app that normally emits deploy events weekly going silent — which pure TTL-on-docs never catches. M2 material: needs cadence history.

### 2.3 Anomaly-learned freshness (no thresholds at all)

- Monte Carlo auto-profiles every table and learns baseline update cadence within ~2 weeks, alerting on freshness/volume/schema anomalies **without configured thresholds**, and traces which dashboards depend on a stale table ([Vimeo's writeup](https://medium.com/vimeo-engineering-blog/monitoring-data-quality-at-scale-using-monte-carlo-934577e45ab0), [tool landscape](https://atlan.com/know/data-observability-tools/)). [Elementary](https://www.synq.io/blog/top-5-monte-carlo-alternatives-for-data-observability) is the dbt-native open-source equivalent for small teams. LOW for Aug-16 (no baselines exist in a greenfield corpus), but the dependency-tracing idea — "which *answers* depend on this stale *entry*" — is worth stealing eventually.

### 2.4 Freshness SLIs/SLOs — the governance vocabulary

- Google's SRE workbook treats freshness as a first-class pipeline SLI: "X% of data processed in Y time" or "**the oldest data is no older than Y**" ([SRE workbook, data processing](https://sre.google/workbook/data-processing/), [GCP SLI metrics for data processing](https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/sli-metrics/data-proc-metrics)). Two transferable rules: **measure freshness at the consumption layer, not ingestion** (ingestion-side freshness doesn't reflect what users see — for the garden: stamp at answer-render time, which is where the projection-lag stamp lands anyway), and **a freshness breach demands a different response than a correctness breach** (wait vs intervene) — useful for calibrating how alarming the navigator's warning banners should sound. Practitioner treatment: [OneUptime on building freshness SLOs](https://oneuptime.com/blog/post/2026-01-30-freshness-slos/view).

## 3. Keeping derived indexes mechanically in sync (the frozen-index fix)

The first pass identified "embedding lag" (Atlan's term) as exactly mahdi's failure but found no *mechanism*. The mechanism exists, off the shelf:

- **LangChain's indexing API + RecordManager** ([announcement](https://blog.langchain.com/syncing-data-sources-to-vector-stores/), [how-to](https://js.langchain.com/v0.2/docs/how_to/indexing/), [API](https://reference.langchain.com/python/langchain-core/indexing)): every document is **content-hashed**; the RecordManager stores hash + source ID + write time; on re-index, unchanged docs are skipped, changed docs are re-embedded, and **stale derived records are deleted** under three cleanup modes — `none` (manual), `incremental` (continuous cleanup of changed sources during indexing), `full` (anything absent from the current load is purged — requires loading the whole corpus). Practitioner walkthrough: [SQLRecordManager in practice](https://dev.to/sreeni5018/building-a-smart-rag-system-how-langchains-sqlrecordmanagers-eliminates-duplicate-processing-and-1mij).
- **The transferable invariant, regardless of framework:** a derived store is valid only while `hash(source) == hash_recorded_at_derivation`; reconciliation must be a scheduled mechanical job (cheap: hashes, not embeddings, are compared), and **deletion of orphaned derived records is part of sync** — the mahdi index kept serving entries whose sources had moved on precisely because nothing ever deleted or re-derived them. In the event-sourced frame this collapses into §1: make the index a projection of knowledge-change events and its checkpoint lag *is* its sync status; the RecordManager pattern is the fallback for sources that don't flow through the bus (git working trees, external docs).
- **Retrieval-side companion — don't over-boost recency:** Glean's relevance engineering balances freshness weights against authority and popularity signals, and their debugging guide warns that an over-tuned recency boost pushes new-but-irrelevant docs above canonical pages; an old doc can be fully authoritative (the Wi-Fi password example) ([How to debug enterprise search relevancy issues](https://www.glean.com/perspectives/how-to-debug-enterprise-search-relevancy-issues)). Age-decay ranking (first pass §4) must be conditioned on the entry's volatility class, not applied uniformly.

## 4. Runbooks: the knowledge class the release actually ships

The first pass treated "docs" generically. For a junior operator running 4-5 apps, the dominant artifact is the **runbook**, and it has its own staleness literature:

- **Quantified failure cost:** 3 stale steps in a 30-step runbook is a 10% error rate; each wrong step costs **8-15 minutes** of confused investigation, which can double or triple a 20-minute incident ([ekline: "Why Your Incident Runbook Lies to You at 3 a.m."](https://ekline.io/blog/why-your-incident-runbook-lies-to-you-at-3-a-m-and-how-to-tell-before-the-page-fires)). Runbooks are "written when systems are healthy" and are most stale exactly when most needed.
- **Mechanism 1 — bind steps to live system facts:** a step saying "check queue depth on the orders worker" must reference **the actual dashboard panel by URL with the query embedded**, so when the panel moves or the query stops returning data the runbook *breaks visibly* instead of decaying silently (ekline). This is the ops-flavored version of Fiberplane's code anchors, and it's an authoring convention, not a tool — adoptable by Aug 16. For the garden: runbook-class knowledge entries should carry resolvable references (Grafana panel URLs, `kubectl`/kploy commands, bus topic names) that a nightly job can dereference; a dead link ⇒ entry flagged broken.
- **Mechanism 2 — game days against the runbook itself:** planned exercises whose purpose is validating the *document*, not the responders (endorsed by NIST SP 800-61 per ekline). Post-release cadence candidate, and each game day resets `verified`.
- **Mechanism 3 — two timestamps, runbook edition:** track "last updated" *and* "**last validated**" (when the runbook was last tested or confirmed working), plus team-not-individual ownership ([upstat runbook guide](https://upstat.io/blog/runbook-procedures-guide)). Independent confirmation, from the ops world, of the first pass's two-date model — with the stronger reading that for procedures, `verified` should mean *executed successfully*, not *re-read*.
- **Change-process integration:** runbooks live in a repo, ship in PRs, and link to the change that prompted them (ekline) — congruent with kploy's manifests-in-repo model, so runbook updates can be demanded in the same PR that changes deployment config.

## 5. Odds and ends the first pass missed

- **Derive `updated` from git — never store it.** [mkdocs-git-revision-date-localized-plugin](https://github.com/timvink/mkdocs-git-revision-date-localized-plugin) and Docusaurus [`showLastUpdateTime`](https://github.com/facebook/docusaurus/discussions/7229) render per-page last-modified from git history at build time. Trivial, but it halves the two-date maintenance burden: only `verified` requires a human act; `updated` is `git log -1 --format=%cI -- <file>`. A stored `updated` field is itself a staleness liability (the Docusaurus discussion is literally about the derived date being wrong in dev mode — even the *derivation* needs care, but at least it can't silently rot).
- **Backstage Tech Insights as the governance pattern (not the tool):** scheduled **fact retrievers** (including a `techdocsFactRetriever` for docs presence/metadata) feed declarative **JSON-rules-engine checks** rendered as per-entity **scorecards** ([Roadie's Tech Insights docs](https://roadie.io/backstage/plugins/tech-insights/), [Backstage TechDocs overview](https://backstage.io/docs/features/techdocs/techdocs-overview)). Context on why it exists: only ~6% of engineers update docs daily ([Port on TechDocs](https://www.port.io/blog/backstage-techdocs-vs-port)). For M2: a per-app "knowledge health" scorecard (has runbook? verified within TTL? references resolve? projection lag < threshold?) is a small cron job away, no Backstage required.
- **Usage-driven staleness detection (kapa.ai):** cluster the assistant's *uncertain* answers over a period, generate summaries of why answering failed, and emit **AI-suggested doc updates**; dashboards surface top unanswered questions and low-confidence answers ([Coverage Gaps](https://docs.kapa.ai/analytics/coverage-gaps), [perpetual feedback loop](https://www.kapa.ai/blog/how-to-turn-your-docs-ai-chat-into-a-perpetual-feedback-loop)). Inverts the direction of every mechanism above: instead of checking sources, mine the *query stream* for evidence of staleness/gaps. Greenwood's bus makes this cheap at M2 — navigator answers are already events; a projection over `answer.confidence == low` is the gap report.
- **2026 agent-memory practice converges on the same design:** guidance now explicitly names staleness as the failure where "the outside world changes but system memory doesn't," recommends a **staleness penalty weighted by time-since-last-verification inside retrieval scoring**, and frames memory as a **"hint surface rather than authoritative fact"** — stale memories aren't auto-trimmed but are *ignored when verification fails*, so the agent "never silently asserts stale facts" ([AI Agent Memory Design Guide](https://hidekazu-konishi.com/entry/ai_agent_memory_design_guide.html), [Zylos on agent memory architectures](https://zylos.ai/research/2026-04-05-ai-agent-memory-architectures-persistent-knowledge/), [Nicolas Bustamante, Agent Memory Engineering](https://nicolasbustamante.com/blog/agent-memory-engineering)). "Hint, then verify" is good spec language for how the navigator should treat authored KB entries when making operational claims.

## 6. Synthesis: what this changes about the first pass's release plan

(Inference, mine.) The first pass's recommendations 1-8 stand, but the event-sourcing findings **restructure** them:

1. **Partition the KB by freshness mechanism.** Projected knowledge (derived from bus events): freshness = checkpoint lag, stamped per answer, alerted via consumer-lag monitoring — no frontmatter needed. Authored knowledge (decisions, rationale, runbooks): two-date frontmatter with `updated` derived from git and `verified` human-set, dbt-shaped `warn_after`/`error_after` tiers.
2. **Triage reads by criticality** (EventSourcingDB pattern): critical operational claims → live check against log head / live system; routine → projection + lag stamp; historical → authored entry + verified stamp.
3. **Runbooks get the strictest contract:** live-fact bindings (URLs/commands that a nightly job dereferences), `verified` means *executed*, and short `warn_after`.
4. **Any derived index ships with a reconciliation job** (content-hash RecordManager pattern or projection checkpoint) whose lag/last-run is itself monitored. An index without a sync job is a release blocker, not a nice-to-have — it is the exact mahdi failure.
