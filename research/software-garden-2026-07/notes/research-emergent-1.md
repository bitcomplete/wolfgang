# Keeping agent-facing knowledge fresh: staleness detection and authority calibration

**Research question:** What public techniques, tools, and research exist for (a) detecting staleness/drift in documentation and knowledge bases that agents answer from, and (b) making an AI system's confidence proportional to the age and verification status of its data?

**Context (garden-specific):** Discovery found mahdi answering authoritatively from state frozen ~7 weeks (72 dirty git entries, merge conflicts its own index claims are fixed) while its push-based update protocol went unused; Chattermax's README is badly stale versus its code. The late-July 2026 release puts a junior engineer — who will not push back on a confident wrong answer — in front of navigator answers about 4-5 running apps.

## 1. Docs-as-code drift detection (structural, CI-time)

The most mature public pattern: **anchor documentation to specific code locations, fingerprint the code, and fail CI when the anchored code changes without the doc changing.**

- **Fiberplane `drift`** ([repo](https://github.com/fiberplane/drift), [blog](https://fiberplane.com/blog/drift-documentation-linter/)) — markdown docs carry anchors in frontmatter or inline: `path` (required), optional `#Symbol`, optional provenance commit SHA, e.g. `src/auth/provider.ts#AuthConfig@a1b2c3d`. It parses code with tree-sitter and stores a **normalized AST fingerprint** (node kinds + token text, no whitespace/position), so reformatting doesn't false-positive but logic changes do. `drift check` yields three statuses per anchor: **fresh / stale (code changed since provenance) / broken (file or symbol gone)**. Explicit AI-agent rationale from the author: agents "are prolific code changers but terrible at knowing what else their change affects" — the CI gate forces agents to acknowledge docs alongside code changes. Deliberately avoids LLM checks as "expensive for what should be a trivial staleness check." Languages: TypeScript, Python, Rust, Go, Zig, Java.
- **Dosu's freshness-in-CI recipe** ([blog](https://dosu.dev/blog/score-documentation-freshness-in-ci)) — a deterministic 0-100 score per doc page: `freshness = max(0, 100 - age_penalty - drift_penalty - ttl_penalty)`. Age penalty (capped 30) = doc timestamp lagging the timestamps of the code it references (via `git log --follow` / `git blame`); TTL penalty = 2 pts/day past a per-page `ttl_days` declared in frontmatter; drift penalty = 10 pts per backticked symbol that no longer exists in source (capped 40). Frontmatter maps each doc to `sources:` globs. CI posts per-PR score deltas, enforces SLOs (median ≥ 75; critical pages must stay > 60), and routes **gray-zone pages (35-64) to Claude Code for semantic validation** — LLM judgment only where deterministic signals are ambiguous. Companion post: [catching doc drift with Claude Code + GitHub Actions](https://dosu.dev/blog/how-to-catch-documentation-drift-claude-code-github-actions) using `anthropics/claude-code-action@v1` on merge to main.
- **Swimm Auto-sync** ([blog](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work)) — commercial precedent: doc "snippets" coupled to code, verified fast enough to run in CI and locally pre-commit; blocking PRs on stale docs is opt-in.
- **API-spec drift**: **oasdiff** ([repo](https://github.com/oasdiff/oasdiff), [GH Action](https://github.com/oasdiff/oasdiff-action)) diffs OpenAPI specs with 300+ change rules in CI; Optic was archived Jan 2026 ([post-mortem comparison](https://dev.to/flarecanary/optic-is-dead-what-now-for-api-drift-detection-2kb8), [2026 tool comparison](https://dev.to/flarecanary/api-schema-drift-detection-tools-compared-2026-1ib4)). Pattern: derive the spec from code (or test traffic) and treat divergence as a build failure.
- **Others seen:** [drift-vscode](https://github.com/pallaprolus/drift-vscode) (AST-based doc/code governance in-editor), a [Documentation Drift Detector Claude Code skill](https://mcpmarket.com/tools/skills/documentation-drift-detector), [doc-drift-in-CI overview](https://understandingdata.com/posts/doc-drift-detection-ci/), "Docvet" (default thresholds: 30-day drift, 90-day age — mentioned in the Dosu post; not independently verified).

**Academic line — obsolete comment detection:** "Just-In-Time Obsolete Comment Detection and Update" (IEEE TSE, CUP² two-stage detector+updater: [paper](https://ieeexplore.ieee.org/document/9664004/), [PDF](https://yanmeng.github.io/papers/TSE221.pdf)); HatCUP ([arXiv 2205.00600](https://arxiv.org/pdf/2205.00600)); data-quality study ADVOC ([ICSE 2023](https://cs.nju.edu.cn/yuanyao/static/icse2023a.pdf)); SEOCD ([ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0957417425010929)). Decade-old, well-replicated finding: developers change code and neglect co-located prose, and detection at change time (JIT) beats periodic audits.

## 2. Freshness metadata and last-verified stamps (governance layer)

- **Google's internal practice** (*Software Engineering at Google*, [ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)) — documents carry **freshness dates** (last review time); metadata sends **email nags when a doc hasn't been touched in e.g. three months**; g3doc keeps docs next to code so one change updates both ([summary](https://www.paleblueapps.com/rockandnull/google-documentation-as-code-best-practices/), [Addy Osmani's applied notes](https://addyo.substack.com/p/applied-software-engineering-at-google)). This is the canonical citation for "docs expire unless re-verified."
- **The two-date model** — the recurring core primitive across sources: `updated` (content last modified) **vs** `verified` / `last_verified` (last human/source confirmation). **The gap between them is the primary staleness signal.** Articulated by [Scott Curtner's OKF freshness extension](https://www.scottcurtner.com/articles/okf-freshness/) and [Atlan's staleness](https://atlan.com/know/llm-knowledge-base-staleness/) / [freshness-scoring](https://atlan.com/know/llm-knowledge-base-freshness-scoring/) writeups.
- **Google Cloud Open Knowledge Format (OKF), v0.1, released 2026-06-12** — verified real via multiple outlets ([Google Cloud blog](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing), [MarkTechPost](https://www.marktechpost.com/2026/06/16/google-cloud-introduces-open-knowledge-format-okf-a-vendor-neutral-markdown-spec-for-giving-ai-agents-curated-context/), [The Decoder](https://the-decoder.com/google-clouds-open-knowledge-format-turns-scattered-docs-into-markdown-files-for-ai-agents/)). Vendor-neutral spec: a directory of markdown files with YAML frontmatter, cross-links form the knowledge graph; only `type` is required; `updated` timestamp is **optional** and there is **no native verification/review field** — OKF is deliberately silent on lifecycle. Curtner's extension layers on: two-date frontmatter, a weekly review queue sorted by oldest `verified`, and **per-document review contracts** (frequency, mode — factual/status/process/generative — and focus areas). Directly relevant: wolfgang/mahdi knowledge bases are already markdown-with-frontmatter, so OKF-compatible freshness fields are a near-zero-cost adoption.
- **Atlan's operational framework** ([freshness scoring](https://atlan.com/know/llm-knowledge-base-freshness-scoring/)) — minimum fields per doc: `last_verified`, `updated_at`, `owner`. Composite 0-100 score over four dimensions: content age, **embedding lag** (doc updated but index not re-embedded — exactly mahdi's frozen-index failure), stale-retrieval rate (fraction of recent queries answered from out-of-threshold docs), coverage drift (% of corpus past threshold). Criticality-tiered thresholds (zero-staleness for safety/pricing; 24h for procedures; 30d reference; 90d background). Alerts < 85; **application-layer degraded-mode warning < 70**. Remediation: strip a `certified_for_ai: true` flag (pull doc from active retrieval), notify owner, queue recertification. Caveat: Atlan is a vendor writing marketing-adjacent guidance; the framework is sensible but not a neutral standard.
- **Giant Swarm `frontmatter-validator`** (via the [Dosu post](https://dosu.dev/blog/score-documentation-freshness-in-ci)) — open-source, in production: gates their public docs in CI on `last_review_date` against a configurable `REVIEW_TOO_LONG_AGO` window. The simplest deployable version of review-date enforcement.
- KB-audit practice generally: freshness measured as % of top-viewed docs verified in last 60-90 days ([knowledge-base.software audit guide](https://knowledge-base.software/guides/knowledge-base-content-audit/)).

## 3. Derived vs stored documentation state

- The through-line in every tool above: **make doc state derived where possible, and where it must be stored prose, bind it to the derivation source and verify the binding mechanically.** oasdiff (spec derived from code / verified against traffic), drift's anchors (prose bound to AST fingerprints), Dosu's `sources:` globs (prose bound to file sets).
- **Agent-instruction files are the same problem:** CLAUDE.md/AGENTS.md drift is now a recognized failure class — "most instruction drift is boring... one stale command, one missing paragraph" ([Plexus sync guide](https://minilv.github.io/Plexus/how-to-keep-claude-md-and-agents-md-in-sync.html)). Public remedies are all single-source-of-truth + projection: `@AGENTS.md` import into CLAUDE.md so "drift is structurally impossible" ([gist on import/symlink patterns](https://gist.github.com/yurukusa/d36197848911f025add142abefcde685)), or generators like `@mongez/agent-kit` deriving CLAUDE.md/GEMINI.md/copilot-instructions from one AGENTS.md ([dev.to](https://dev.to/hassanzohdy/one-agentsmd-for-every-coding-agent-auto-derive-claudemd-geminimd-copilot-instructions-2053)).
- **Inference (mine):** mahdi's failure is precisely stored-state-presented-as-derived: its index *claims* merge conflicts are resolved (stored assertion) while `git status` (derivable ground truth) says otherwise. Any statement a navigator can recompute from the working tree at answer time should be recomputed, not quoted from the KB; the KB should store only what cannot be derived (decisions, rationale) plus pointers to derivation commands.

## 4. Recency-aware retrieval and grounding

- **FreshLLMs / FreshQA** (Google, 2023) — benchmark + FreshPrompt method for questions whose answers change; introduced a volatility taxonomy (never/slow/fast-changing, false-premise) motivating per-fact freshness classes; re-fetches evidence unconditionally. Referenced across the 2025-26 temporal-RAG literature.
- **Temporal RAG with a recency prior** ([arXiv 2509.19376](https://arxiv.org/abs/2509.19376), "Freshness and the Limits of Heuristic Trend Detection in Temporal RAG") — plain semantic retrieval is atemporal; a **fused score blending cosine similarity with a half-life decay on document age** largely solves the freshness component (simple and deployable); heuristic *trend* detection remains hard. This is the paper-grade version of Elasticsearch-style date-decay ranking.
- **Recency requirements estimation** ([arXiv 2603.16544](https://arxiv.org/html/2603.16544), "How often do Answers Change?") — estimates per-question recency demand, i.e., gate whether fresh retrieval is needed at all based on question volatility.
- **FRESCO** ([arXiv 2604.14227](https://arxiv.org/html/2604.14227v1)) — benchmarks re-rankers on *evolving semantic conflict*: corpus contains both old and new versions of a fact and the ranker must prefer the current one. Freshness-aware caching for open-web RAG: [arXiv 2607.04281](https://arxiv.org/pdf/2607.04281).
- **Bi-temporal agent memory — Zep/Graphiti** ([arXiv 2501.13956](https://arxiv.org/pdf/2501.13956), [Neo4j overview](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/), [Zep explainer](https://www.getzep.com/ai-agents/temporal-knowledge-graph/)) — open-source temporal knowledge graph tracking four timestamps per fact (`created/expired` in-system; `valid/invalid` in-world). On contradiction, the old edge gets `invalid_at` set — **superseded facts are invalidated, never deleted**, so the agent never has to choose between a stale and a current fact, and history is preserved. The strongest public architecture for "authority = validity interval," directly applicable to a navigator's decision log (decisions get superseded, not erased — matches wolfgang's append-friendly convention).
- Related 2026 preprints on stale-fact elimination in agent memory: [arXiv 2606.26511](https://arxiv.org/pdf/2606.26511) (Temporal Validity in Retrieval Memory), [arXiv 2607.01935](https://arxiv.org/pdf/2607.01935) (A-TMA).

## 5. Authority/confidence calibration against data age and verification status

- **Don't ask the LLM to judge freshness** ([arXiv 2606.01435](https://arxiv.org/abs/2606.01435), "Don't Ask the LLM to Track Freshness") — when retrieved memory contains conflicting versions of a fact, deterministic post-retrieval aggregation (pick highest recency serial) beats LLM adjudication by ~+28 points on their benchmarks; the bottleneck is assembly, not storage. Design consequence: **freshness resolution belongs in deterministic pipeline code, with the LLM receiving only the already-resolved, timestamped winner.**
- **Confidence-aware abstention in RAG:** activation-based uncertainty for response abstinence ([arXiv 2510.13750](https://arxiv.org/html/2510.13750)); "Trust or Abstain? A Self-Aware RAG Approach" ([arXiv 2605.18792](https://arxiv.org/pdf/2605.18792)); trustworthy-RAG survey ([arXiv 2502.06872](https://arxiv.org/pdf/2502.06872)); practitioner-level pattern in [Microsoft's "Confidence-Aware RAG"](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/confidence-aware-rag-teaching-your-ai-pipeline-to-acknowledge-uncertainty/4515061) (score retrieval quality; below threshold, say so or abstain).
- **Verbalized uncertainty:** "LLMs Should Express Uncertainty Explicitly" ([arXiv 2604.05306](https://arxiv.org/html/2604.05306v2)) — post-answer verbalized confidence supports user trust and retrieval gating. Caution: **retrieval-state lock-in** ([arXiv 2606.22728](https://arxiv.org/pdf/2606.22728)) shows answer-side confidence gates can fail to notice that retrieval itself returned stale/irrelevant context — model-internal confidence is *not* a substitute for metadata-driven staleness signals.
- **Synthesis (inference, but well-supported):** the public evidence converges on *metadata-conditioned* authority rather than model-estimated confidence — i.e., the system computes a freshness/verification status deterministically (two-date gap, drift status, validity interval) and **injects it into the prompt and the rendered answer** ("last verified 2026-06-03; source file changed since"), optionally degrading to hedged phrasing or refusal below thresholds (Atlan's <70 degraded mode; Dosu's certified-for-retrieval gating). Nobody credible proposes letting the model self-assess whether its KB is stale.

## Implications for the late-July release

The release-defining constraint: **a junior engineer will take a confident navigator answer at face value.** Every mechanism below exists publicly and is deterministic; none requires trusting the model to notice its own staleness.

1. **Adopt the two-date frontmatter now** on every knowledge entry in wolfgang/mahdi: `updated` + `verified` (+ `owner`, `sources:` globs where the entry describes code). The KBs are already markdown+frontmatter, so this is additive and OKF-aligned. The updated/verified gap becomes the machine-readable staleness signal.
2. **Age-stamp every answer, unconditionally.** Each navigator answer must render the provenance line: what entries it drew on, their `verified` dates, and whether their `sources` have changed since (drift status). This is the cheapest calibration lever and the direct fix for "confident answer from 7-week-frozen state."
3. **Derive, don't quote, anything recomputable.** Answers about repo/runtime state (git status, merge conflicts, deploy versions of the 4-5 apps) must come from live commands at answer time, not from stored index text. Store in the KB only non-derivable knowledge (decisions, rationale) plus derivation pointers. This single rule would have prevented the mahdi incident outright.
4. **Deterministic staleness gate with tiered behavior** (Atlan/Dosu pattern): fresh → answer normally with stamp; past TTL or sources-drifted → answer prefixed with an explicit warning banner ("this entry was last verified N weeks ago and the code it describes has changed — verify before acting"); badly stale on operationally critical topics → refuse to answer authoritatively and emit the verification command instead. Thresholds per entry class (runbook/procedure: days; architecture rationale: months), declared as `ttl_days` in frontmatter.
5. **Put drift checking in CI, not in audits.** A pre-answer or nightly job (Fiberplane-drift-style anchors, or the simpler Dosu symbol-existence check) marks entries fresh/stale/broken; a Giant Swarm-style frontmatter validator fails builds on missing/expired `verified` dates. The push-based update protocol demonstrably goes unused — pull-based mechanical checks must be the backstop, with review-nag emails (Google model) as the human loop.
6. **Supersede, never overwrite, decisions** (Graphiti model): decision entries get `superseded_by`/`invalid_from` rather than edits, so the navigator can always distinguish current from historical without an LLM judgment call — and resolution of conflicts happens in pipeline code (pick latest valid), per arXiv 2606.01435.
7. **Do not build model-confidence-based freshness for this release.** The research (retrieval-state lock-in; "don't ask the LLM to track freshness") says internal confidence misses stale-context failures. Metadata-conditioned stamps + gates are both easier to ship by end of July and better supported by evidence.
8. **Scope for July:** items 1-3 plus the warning-banner tier of item 4 are shippable in days and cover the observed failure modes; anchors/AST fingerprinting (item 5's fuller form) and bi-temporal decision graphs (item 6 beyond a frontmatter convention) are post-release hardening.
